# 熱・LES・物性評価のGPU化（2026-09-17）

`study.device = cuda:0` の標準実行で、XLBの流れに加え、熱輸送、共役熱伝達、Smagorinsky LES、温度依存物性をGPU上で処理します。途中結果保存を無効にした場合、反復中は安定性判定・履歴用の集計値だけをCPUへ返し、全計算場は最後の保存時に1回の一括呼び出しで取得します。時系列表示を有効にした場合は指定したステップで追加転送します（[時系列表示](transient-results.md)）。以下の速度比較は途中結果保存なしで測定しました。メッシュ生成、ZIP/NPZ/VTK書き出しはCPUです。

## 実装

- LBMの衝突・ストリーミング・流体境界処理をJAXでまとめてコンパイル。
- `fields_jax.py`: 温度表の補間、材料割り当て、LESの速度勾配と渦動粘度。
- `thermal_jax.py`: 移流、流体・固体間の調和平均熱伝導、箱/CAD面の温度・熱流束・対流条件、安定性係数。
- 温度・物性・LESはFP64を維持。LBMの分布関数と保存結果場は従来どおりFP32。
- CPU版のNumPy熱処理を比較基準として保持。GPUが使えない場合の暗黙のCPU切替は行わない。
- `jax.device_get` の実呼び出しを監視する独立テストにより、毎ステップの進捗表示でも全場の取得が最後の1回だけであることを確認。

## RTX 3060での比較

同じGPU・入力・出力頻度で、旧Dockerイメージ `xlb-workbench:before-gpu-thermal` と新イメージを別プロセスで実行。水＋温度依存熱伝導率を持つ鋼の固体、LES有効、上面加熱のケースです。

|条件|旧版 秒/ステップ|GPU化後 秒/ステップ|反復部の速度比|全体時間 旧→新|
|---|---:|---:|---:|---:|
|37.5万セル、40ステップ|0.3418|0.0544|6.28倍|22.85→17.17秒|
|300万セル、20ステップ|2.1552|0.0942|22.88倍|67.69→36.10秒|

秒/ステップは初回5ステップ区間を除いた進捗区間の平均で、安定性チェックと集計を含みます。全体時間はXLB初期化・JIT・最終評価・ファイル保存を含み、メッシュ生成とコンテナ起動を含みません。各条件1回の測定であり、すべての形状や長時間計算で同じ倍率を保証するものではありません。

300万セルで保存された全場の旧版との最大絶対差:

|場|最大差|
|---|---:|
|速度|2.03×10⁻⁷ m/s|
|温度|3.05×10⁻⁵ K|
|圧力|1.02×10⁻⁴ Pa|
|渦動粘度|1.38×10⁻¹² m²/s|

両サイズでマスクと材料割り当ては完全一致し、場の比較も設定した許容差内です。これは実装間の整合性確認であり、乱流精度や格子収束の検証ではありません。

入力、各進捗時刻、診断、ソースSHA-256、差分は [37.5万セル](gpu-pipeline-375k.json) と [300万セル](gpu-pipeline-3m.json)。元の計算場は `data/development_archive/pipeline-benchmark/{before,after}-{375k,3m}/` に保持しています。比較後のソースがベンチマークのSHA-256と一致することも確認しました。

## 検証と稼働

- 自動テスト64件成功（WSL、25.866秒、スキップなし）。CPU基準、物性表、CAD、CHT熱量保存、安定性、保存、停止を含む。
- CUDA上で物性・LESの6件、熱処理の5件の単体テスト成功。
- GPU搭載Docker環境でCPUデバイスへ強制したJAX処理の統合テスト5件成功。
- 稼働中のDockerサーバーへ同条件のCPU/CUDA各100ステップを送信し、実デバイス、固体温度、渦動粘度、全場差分、一括転送回数を確認。記録は [HTTP実行](gpu-pipeline-verification.json)。
- 23度回転したCADに入口・出口・加熱面を個別指定し、CUDAで60ステップ完了。記録は [CAD実行](gpu-pipeline-cad-verification.json)。
- 3種類の保存例を独立した一時ストアへ復元し、計算場・CAD面参照・出典情報を確認。GUIでも最新のCUDA実行を開き、流体・固体を含む温度断面（293.1～314.0 K）を表示確認。
- CPU/GPU両イメージを再ビルド。通常起動先は `http://127.0.0.1:8766/`、既存の `data/` を継続使用。

## 残る律速

300万セルの新しい実行では、最終評価・取得・圧縮NPZ・テキストVTK等の保存が約17.1秒を占めました。短い実行では初回JITも大きいため、反復部22.9倍に対して全体の速度比は1.88倍です。

CADメッシングと保存は引き続きCPU処理です。反復中も小さな安定性判定の同期があり、小規模格子ではその呼び出し負荷が目立ちます。今後は保存形式のバイナリ化、コンパイルの再利用、判定の一括化が改善候補です。

## 再実行

```sh
python scripts/verify_gpu.py --output docs/gpu-pipeline-verification.json
python scripts/verify_cad_gpu.py --output docs/gpu-pipeline-cad-verification.json
python -m scripts.verify_archives
```

Dockerイメージ内で `scripts/` を `/app/scripts:ro` に、結果ディレクトリを `/bench` にマウントし、`python -m scripts.benchmark_pipeline --cells 100 --steps 20 --output /bench/after-3m` を実行すると300万セルの測定を再現できます。保存先を変えて比較結果を上書きしないでください。

`XLB_COMPUTE_BACKEND=auto` が標準です。`.env` で `reference` にすると指定したデバイスでLBMを実行しつつ旧NumPy熱処理を使用し、`device` にするとCPU指定でもJAX処理を使用します。変更後は同じCompose構成で再作成します。入力JSONの変更は不要です。
