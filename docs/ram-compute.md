# GPU＋RAM で大きな格子を計算する

解析設定 → 実行デバイス → **GPU＋RAM（大規模・低速）** を選びます。CUDA版Dockerイメージが必要です。GPU バッチセル数の初期値は65,536。小さくするとVRAM使用量が減り、大きくすると転送回数が減ります。設定範囲は1,024〜1,048,576です。

全領域のD3Q27分布関数・温度・物性・境界マスクをCPU RAMに置き、セルごとに独立したXLB平衡分布・BGK衝突計算を小分けでGPUに送ります。結果をRAMへ戻してから、CPUで全領域の移流・境界処理・熱輸送・LESを計算します。セル数がバッチの整数倍でなくても末尾を処理します。格子を分割した位置に新たな壁や周期境界は作りません。

通常のCUDAモードは全計算場をGPUに保持する高速な方式です。GPU＋RAMモードは全領域をGPUに確保せず、VRAM使用量をバッチ数で抑える方式です。OSの自動ページング、VRAMとRAMの単純な合算、ディスクを使う計算ではありません。熱・LESまでGPUで分割する方式にはまだ対応していません。熱だけの計算ではGPU衝突処理を行わず、CPU上で進みます。

## 容量と速度の制約

重力・浮力を有効にすると、衝突バッチへの転送が 12 bytes/セル/ステップ増え、加速度場などの RAM も追加で使います。下記の大規模容量測定は重力無効時の値です。機能の説明は [重力・浮力](gravity.md) を参照してください。

- 全領域は引き続きRAMに収まる必要があります。D3Q27の分布関数1組だけで108 bytes/セルです。実際には新旧分布、移流の作業領域、熱・LES・物性・結果保存の配列が必要で、この値より大幅に増えます。CAD面の数・有効なモデル・JAXの作業領域でも変わるため、108 bytesから最大セル数を算出しないでください。
- 流れの1ステップごとに約128 bytes/セルをGPUへ送り、108 bytes/セルを戻します（末尾パディング分を除く）。転送帯域とCPUの移流・熱・LESが主な律速になります。通常CUDAより遅く、ケースによってCPU単独よりも遅くなります。
- 途中結果1枚は約24 bytes/セルに静的マスクが加わります。大規模計算では結果保存間隔を広げるとI/O負荷を減らせます。VTK出力は巨大な文字列を一括生成せず逐次書き出します。
- 許容メッシュ数のサーバー上限（既定1,000万セル、各軸1,024）は別の制約です。RAMモード選択だけで上限や確保可能なRAMは変わりません。
- CUDAが使えない環境ではエラーを返します。CPUのみでRAMを使う場合は既存の「CPU（標準）」を選んでください。

結果の診断には `compute_backend=ram`、`state_device`、`collision_device` と `ram_offload` を保存します。バッチ数・実際の転送量・GPUアロケータ統計を確認できます。アロケータ統計はCUDAコンテキストや他プロセスを含めた `nvidia-smi` の値とは異なります。

途中結果、停止、完了後リスタート、プロジェクト保存・ZIP移送にも対応します。バッチサイズは物理条件の互換性判定から除外されます。UIからのリスタートは元実行のデバイス・バッチ設定も引き継ぎます。

## このPCのRAM割り当て

2026-09-17時点の確認値は、RTX 3060のVRAM 12 GiB、Windows物理RAM約32 GiB、WSLから見えるRAM約16 GiBです。従って現状ではWindowsの32 GiB全部を解析に使えるわけではありません。

WSL2のメモリ上限はユーザーフォルダーの `.wslconfig` の `[wsl2] memory` で設定できます。例えば32 GiB機でWindows側の余裕を確認した上で `memory=24GB` とする方法があります。設定の反映にはWSLの再起動が必要で、Dockerを含むWSL上の処理も停止します。本変更ではこのマシン設定とWSLの稼働状態を変更していません。詳細は [MicrosoftのWSL設定](https://learn.microsoft.com/ja-jp/windows/wsl/wsl-config) を参照してください。

実装は明示的なCPU/GPU間転送を使います。JAXのGPUメモリ予約率を変えるだけではRAMへ自動退避する計算になりません。参考: [JAX GPU memory allocation](https://docs.jax.dev/en/latest/gpu_memory_allocation.html)、[JAX host offloading](https://docs.jax.dev/en/latest/notebooks/host-offloading.html)。

## 実機確認

RTX 3060、バッチ65,536セルで、流れ＋熱＋LESの3ステップ計算を実行し、最終結果とリスタートファイルまで保存しました。途中スナップショットは無効です。

| 総セル数 | ピークRAM（プロセスRSS） | GPUアロケータのピーク | 保存を含む所要時間 |
| --- | ---: | ---: | ---: |
| 375,000 | 1.46 GiB | 137.25 MiB | 17.4秒 |
| 3,000,000 | 3.81 GiB | 137.25 MiB | 51.3秒 |
| 9,725,376 | 9.00 GiB | 137.25 MiB | 163.6秒 |

GPU欄はJAXの確保量で、ドライバ・CUDAコンテキスト・他プロセスのVRAMは含みません。約973万セルでは反復終了が約59.5秒、全保存終了が約163.6秒で、約780 MBのASCII VTK等の書き出しも大きな負荷でした。3ステップの実行・容量確認であり、収束済み解析や最大可能セル数を保証する測定ではありません。元記録は [ram-memory-verification.json](ram-memory-verification.json)。

3,456セルの別ケースではLES＋共役熱伝達、熱のみ、流れのみを検証し、CPU基準との場・途中スナップショット比較が許容誤差内でした。同じバッチ設定で7ステップ連続と3＋4ステップ再開は内部状態まで完全一致しました。バッチサイズを変更した再開は許容誤差で比較しています。記録は [ram-gpu-verification.json](ram-gpu-verification.json)。自動テスト115件が成功し、ブラウザからの設定切替・保存・3ステップ実行も確認済みです。
